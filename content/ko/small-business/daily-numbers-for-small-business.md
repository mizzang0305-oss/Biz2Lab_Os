## 합계 하나로는 다음 행동을 고를 수 없다

매장 운영 화면에 “오늘 97건”만 보이면 많아 보이지만 무엇을 해야 하는지는 알 수 없습니다. 신규 주문, 예약 확정, 대기 팀과 고객 메모는 담당자와 마감 조건이 모두 다릅니다. 합계가 같아도 주문 40건과 웨이팅 40팀은 같은 운영 상태가 아닙니다.

`mybizLab`의 공개 데모에서는 고객 기억, 예약, 웨이팅, QR 주문을 서로 다른 카드와 데이터 흐름으로 표시합니다. 외부 공급자가 연결되지 않은 경우에는 `local` 데이터 제공자를 사용하고 화면 전체를 읽기 전용 데모로 고정합니다.

## 화면에서 무엇을 보고 무엇을 믿지 말아야 하나

아래 화면은 실제 매장 매출이나 고객 행동을 보여 주지 않습니다. 읽기 전용 로컬 데모의 가상 지표 카드이며, 봐야 할 부분은 각 숫자가 별도의 이름·단위·후속 행동을 갖는다는 점입니다. 저장 버튼이나 운영 DB 쓰기는 이 캡처 범위에 없습니다.

화면만으로 실제 고객 수, 재방문율, 매출 변화와 AI 예측 정확도는 확인할 수 없습니다. 데모에 표시된 변화율과 숫자는 UI 상태를 보여 주는 fixture이므로 성과 근거로 사용하지 않습니다.

## 지표마다 원본과 기준시각을 붙였다

| 지표 | 원본 후보 | 다음 행동 | 합치면 안 되는 이유 |
| --- | --- | --- | --- |
| 고객 기록 | 방문 메모·동의된 기록 | 재확인 또는 후속 응대 | 주문 건수와 사람 수가 다름 |
| 예약 | 예약 접수와 확정 상태 | 일정·인원 확인 | 문의와 확정을 구분해야 함 |
| 웨이팅 | 입장 대기 등록 | 호출·취소 처리 | 순간 재고처럼 계속 변함 |
| QR 주문 | 주문 원본과 결제 상태 | 준비·취소·환불 확인 | 예약이나 문의와 완료 조건이 다름 |

각 카드에는 값뿐 아니라 단위와 설명을 붙였습니다. 집계 함수가 같아 보여도 원본 엔터티와 기준시각이 다르면 한 SQL 합계로 묶지 않습니다.

## 읽기 전용 데모가 필요했던 이유

운영자가 제품을 살펴보려고 버튼을 눌렀을 때 실제 고객 메모나 예약이 생성되면 안 됩니다. 데모 라우트는 인증된 점주 화면과 분리했고, 수정 동작을 시도하면 읽기 전용 안내만 보여 줍니다. 검색 색인에도 데모 경로를 포함하지 않아 공개 사례와 운영 앱을 혼동하지 않게 했습니다.

구현 중에는 애니메이션 숫자와 차트가 실제 실시간 분석처럼 보일 위험이 있었습니다. 그래서 페이지 설명과 상단 배지에 데모 모드를 표시하고, 콘텐츠에서는 가상 수치가 실제 성과가 아니라는 경계를 반복해서 명시합니다.

## 개인정보를 포함하지 않은 재현 방식

캡처는 `VITE_DATA_PROVIDER=local`, `VITE_APP_RUNTIME_MODE=demo`에서 실행했습니다. 캡처 대상은 상단 지표 영역으로 제한했고 고객 메모 목록은 포함하지 않았습니다. 자동 검사에서 전화번호, 이메일, 주민·사업자번호 형태, 계좌와 credential 형태, 로컬 절대 경로를 찾으면 이미지 저장 전에 중단합니다.

이 절차가 데모 전체의 개인정보 안전성을 영구 보장하는 것은 아닙니다. fixture가 바뀌면 다시 캡처하고 사람 검토를 거쳐야 합니다.

## 실제 조직에 적용할 때의 순서

1. 숫자마다 원본 시스템과 담당자를 적습니다.
2. 건수, 사람 수, 금액과 상태를 같은 합계로 만들지 않습니다.
3. 기준시각과 늦게 반영된 취소·수정 규칙을 정합니다.
4. 카드마다 숫자가 바뀌었을 때 할 행동을 하나 연결합니다.
5. 데모·테스트·운영 데이터 제공자를 화면과 로그에서 구분합니다.

원본 주문을 먼저 정리해야 한다면 [주문 채널 분리 사례](/ko/small-business/unify-order-channels)에서 내부 주문번호와 채널 원본을 함께 남긴 이유를 확인할 수 있습니다.
