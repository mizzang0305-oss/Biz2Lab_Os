## 결과를 만드는 일과 밖으로 보내는 일은 다르다

콘텐츠 자동화 프로젝트를 만들 때 가장 먼저 부딪힌 문제는 생성 품질이 아니었습니다. 초안이 생겼다는 이유만으로 게시, 업로드, 댓글 작성 같은 외부 동작까지 이어지면 작은 설정 오류가 공개 사고가 됩니다. 그래서 `commerce-automation`에서는 생성 결과와 외부 실행을 서로 다른 단계로 두고 기본값을 `generate-only`로 유지했습니다.

이 사례에서 자동화가 할 수 있는 일은 후보 수집, 초안 생성, 자산 준비와 상태 요약입니다. 사람은 원본 상품, 고지 문구, 계정, 공개 범위와 차단 사유를 확인합니다. 서버 실행은 이 검토와 정확한 승인 문구가 모두 통과한 뒤에만 다음 경계로 이동하도록 설계했습니다.

## 화면에서 봐야 할 부분

아래 화면은 공개 플랫폼의 실제 계정 화면이 아니라 로컬에서 실행한 준비 대시보드입니다. `can_upload=false`, 현재 차단 이유, 다음 조치가 한 영역에 있고 token이나 client secret 값은 표시하지 않습니다. 봐야 할 것은 성공 버튼이 아니라 **왜 아직 실행할 수 없는지 운영자가 읽을 수 있는가**입니다.

화면으로 확인되는 것은 UI와 서버 준비 모델이 차단 상태를 표현한다는 사실입니다. 실제 YouTube·TikTok·Threads 업로드 성공, 공급자 quota, 매출 증가와 운영시간 절감은 이 화면으로 입증할 수 없습니다.

## 승인 경계를 나눈 방식

| 경계 | 시스템이 남기는 것 | 다음 단계 조건 |
| --- | --- | --- |
| 생성 | 초안과 산출물 식별자 | 원본과 결과가 구분됨 |
| 준비 점검 | 자산·권한·정책 상태 요약 | 비밀값 없이 차단 이유 확인 |
| 사람 검토 | 승인 또는 반려 판단 | 검토자와 대상이 명확함 |
| 실행 게이트 | 정확한 승인 문구와 공개 범위 | 서버 조건을 모두 재검증 |
| 결과 기록 | 성공·실패와 안전 메시지 | 실패 후 재시도 여부 판단 |

UI에서 버튼을 숨기는 것만으로는 부족합니다. 요청을 받는 서버도 `PUBLIC_UPLOAD_ENABLED=false`, 공개 범위 제한, 준비된 자산 존재 여부를 다시 검사해야 합니다. 이중 경계가 없으면 다른 클라이언트나 직접 API 호출로 UI 차단을 우회할 수 있습니다.

## 구현하면서 막힌 부분

로컬 Windows 경로에 있는 token 파일과 영상 자산은 개발 컴퓨터에서는 읽을 수 있지만 serverless 배포 환경에서는 같은 경로가 존재하지 않습니다. 이를 성공처럼 포장하지 않고 “로컬 진단 가능”과 “배포 환경에서 실행 가능”을 별도 상태로 만들었습니다. 자산이 준비되지 않으면 업로드 패키지를 만들지 않고, 공급자 구현이 없는 채널은 readiness-only로 표시했습니다.

또한 승인 문구를 단순 체크박스로 대체하지 않았습니다. 실제 영향이 있는 작업은 사용자가 실행 대상을 다시 읽고 정확한 문구를 입력해야 합니다. 이 방식이 모든 사고를 막지는 못하지만, 우발적 클릭과 자동 연쇄 실행을 분리하는 명시적 마찰이 됩니다.

## 개인정보와 운영정보를 뺀 재현

캡처에는 계정명, 채널명, token 값, 로컬 파일 경로와 실제 영상이 없습니다. 환경변수는 이름과 안전한 boolean 상태만 표시되고 값은 렌더링하지 않습니다. 자동 캡처도 `localhost`만 허용하며 DOM에서 이메일, 전화번호, 계정번호 형태와 절대 경로를 검사한 뒤 WebP로 변환합니다.

fixture나 로컬 데모라는 표시가 있어도 실제 고객 사례가 되는 것은 아닙니다. 이 기록은 어떤 승인 경계를 코드와 화면에 배치했는지 설명하는 구축 사례입니다.

## 다른 팀이 적용하기 전 확인할 것

1. 생성 결과와 외부 실행을 서로 다른 권한으로 분리합니다.
2. 실행 전 원본, 대상 계정, 공개 범위, 자산과 고지 문구를 확인합니다.
3. 비밀값 대신 `ready / blocked / manual_required` 같은 상태 요약만 화면에 둡니다.
4. UI와 서버 양쪽에서 승인 조건을 검증합니다.
5. 실패 로그와 재시도 대상을 남기고 자동 재실행 횟수를 제한합니다.

처음부터 모든 채널을 연결하기보다 [실행·실패 로그를 먼저 만든 사례](/ko/automation/automation-priority-method)처럼 외부 영향이 있는 단계와 수동 확인 대상을 표시한 뒤, 한 개의 내부 초안 흐름에서 승인 경계를 검증하는 편이 안전합니다.
