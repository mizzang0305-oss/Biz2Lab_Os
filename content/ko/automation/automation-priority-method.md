## 자동화가 멈췄을 때 먼저 묻게 되는 질문

업무 자동화를 운영하면 “몇 건 처리했나”보다 “어디에서 왜 멈췄나”가 먼저 필요합니다. 입력이 없었는지, 생성은 됐지만 검토가 끝나지 않았는지, 자산이 부족했는지, 외부 실행이 차단됐는지를 구분하지 않으면 운영자는 같은 작업을 중복 실행하게 됩니다.

`commerce-automation`에서 우선순위를 정할 때도 화려한 채널 연동보다 queue 상태, worker job, 실행 결과와 수동 검토 사유를 먼저 만들었습니다. 기능 수보다 복구 가능성을 우선한 결정입니다.

## 로컬 실행 로그가 보여 주는 것

아래 화면은 fixture 기반 로컬 실행 로그입니다. 실제 공급자 계정이나 공개 게시 결과가 아니라, 실행 결과와 안전 메시지, 실패 상태를 한곳에서 확인하는 UI 구조를 보여 줍니다. 빈 목록이라면 아직 실행 기록이 없다는 사실을 그대로 보여 주며 성공 건수를 꾸며 넣지 않습니다.

이 화면만으로 장기 로그 보존, 운영 장애 복구 시간, 공급자 재시도 성공률을 입증할 수 없습니다. 그런 값은 production 저장소와 실제 장애 기록을 별도로 검증해야 합니다.

## 상태를 하나의 성공 여부로 줄이지 않았다

| 상태 영역 | 남겨야 하는 질문 | 잘못 합쳤을 때 생기는 문제 |
| --- | --- | --- |
| queue | 무엇이 처리 대기 중인가 | 대기와 누락을 구분할 수 없음 |
| worker job | 어떤 실행자가 가져갔는가 | 중복 실행 원인을 찾기 어려움 |
| generated result | 결과물은 생성됐는가 | 실행 실패를 생성 실패로 오해 |
| manual review | 사람이 무엇을 확인해야 하나 | 자동 실행으로 잘못 넘어감 |
| run log | 성공·실패와 안전 메시지는 무엇인가 | 재시도 범위를 정할 수 없음 |

`completed` 하나만 저장하면 생성 완료와 외부 게시 완료가 같은 뜻이 됩니다. 그래서 결과물 준비 상태, 검토 상태와 업로드 상태를 서로 다른 필드로 유지하고, 일부만 성공한 경우도 다시 판단할 수 있게 했습니다.

## 실패를 화면에 남기기 어려웠던 이유

오류 원문에는 로컬 절대 경로, 공급자 응답, 환경변수 이름과 자산 식별자가 섞일 수 있습니다. 원문을 그대로 운영 화면에 출력하면 비밀값과 내부 구조가 노출될 수 있어 사용자용 `safe message`와 내부 진단 정보를 분리했습니다. 캡처 대상에는 안전 메시지만 표시하고 경로와 secret 형태는 사전 검사에서 차단합니다.

또 하나의 문제는 자동 재시도입니다. 원인이 사라지지 않았는데 반복 실행하면 같은 외부 요청을 여러 번 보낼 수 있습니다. retry-safe 식별자와 최대 횟수, 사람 검토 전 정지 상태가 없는 작업은 우선순위에서 뒤로 미뤘습니다.

## 숫자 점수 대신 통과 조건을 쓴 이유

가상 점수로 후보를 80점, 60점으로 나누는 것은 쉬우나 현장 위험을 숨길 수 있습니다. 이 프로젝트에서는 아래 질문 중 하나라도 답할 수 없으면 외부 실행 후보로 올리지 않았습니다.

1. 입력 원본과 최신 시각을 다시 찾을 수 있는가?
2. 같은 작업을 재실행해도 중복 부작용이 없는가?
3. 사람 검토가 필요한 조건을 코드로 판정할 수 있는가?
4. 실패 메시지에서 비밀값과 개인정보가 제거되는가?
5. 실행 결과와 생성 결과를 별도 상태로 보관하는가?

이는 모든 조직에 동일한 우선순위를 강요하는 계산법이 아닙니다. 반복 횟수와 처리시간은 각 현장에서 다시 측정해야 합니다.

## 아직 검증하지 않은 범위

로컬 fixture는 상태 모델과 화면 렌더링을 확인하는 데 충분하지만 실제 공급자의 rate limit, 인증 만료, 장기 로그 보존과 운영자 교대 상황은 검증하지 못합니다. 실제 공개 업로드 성과나 절감 시간도 측정하지 않았습니다.

다른 팀이 적용할 때는 [승인형 자동화 사례](/ko/automation/ai-business-automation-guide)와 함께 읽고, 먼저 읽기 전용 queue와 실패 로그를 만든 다음 외부 실행 권한을 연결해야 합니다. 로그가 없는 자동화는 빨라 보여도 실패한 순간 수동 업무보다 복구가 어려워집니다.
