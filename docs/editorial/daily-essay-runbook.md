User authorization (2026-11-02, Asia/Seoul): preserve and improve the existing site, publish one carefully researched new essay each day starting today, and continue beyond the original 30. This authorizes scoped edits, isolated branches, checks, PRs, merges and production publication. It does not authorize invented experience, copied articles, unsupported claims, paid services or unrelated account changes. AdSense approval is not guaranteed by any publishing cadence, word count or topic.

## Start from current state

1. Read the latest user instructions, repository AGENTS.md and installed Next.js documentation required there. Fetch current master and inspect open daily-publication PRs and the latest deployment. Preserve user changes by using an isolated worktree. Do not reset the user's original workspace.
2. Resolve today's calendar date in Asia/Seoul. Read `data/knowledge-release-dates.json`, the plan, manuscripts and `reports/daily-publications/`. Confirm the live URL for any entry already bearing today's date. If today's new essay is live, verify it and finish without publishing a second. If an earlier run has an unfinished PR or deployment, resume it rather than duplicating it. Do not make up missed days with batch posts.
3. Review recent topics and select one distinct reader question within the existing six knowledge-essay themes. Read adjacent essays in full. A new title on the same explanation is insufficient. Avoid keyword-led topic changes, unsupported medical/financial advice and claims of first-hand experiments that never occurred.

## Editorial quality gate

- Give the reader a concrete answer and something to inspect or use: an independently worked example, a primary-record comparison, a transparent calculation or an explanatory diagram. Depth follows the question; no padding, paraphrase chains or templated filler.
- Open relevant primary sources and verify important claims. Record their exact URLs, what each supports, dates and limits of access. Prefer papers, original historical records, official datasets and institutional documentation. Search Korean and international sources as relevant. Do not cite search snippets as if the full source was read. Respect quotation and source-use limits.
- Distinguish established facts, the article's interpretation and clearly labeled hypothetical examples. Independently recompute every numerical example. Do not claim user testing, interviews, traffic, expertise, credentials or outcomes without actual evidence. Dates and author information must be accurate.
- Use an accurate title, a useful description, a clear opening, coherent sections and meaningful related-reading links. The repository currently validates a body of at least 3,500 characters, 3–8 H2 sections and 3–8 sources; these are local format constraints, not Google's approval requirements. Choose a question that merits this format rather than stretching a short answer.
- Add a self-contained, accessible diagram when it explains the point. For photographs, verify reuse rights, attribution and relevance. Do not add an unrelated image just to satisfy an image count. Verify figures against the text, include useful alt text and captions, and mark synthetic data explicitly.
- Re-read the complete rendered article for contradictions, repetition, overstated causal claims, broken references and mobile readability. A technical pass does not replace this editorial review. Revise or choose a better-supported subject when necessary.

4. Generate the OG subset font with the repository font-preparation script and pinned licensed source as documented in `assets/fonts/README.md`. Verify glyph coverage and provenance. Never allow the new title's missing characters to make the OG route fail.
5. Add a review record in `reports/daily-publications/YYYY-MM-DD.md`: reader question, distinction from existing essays, sources actually opened, original contribution, checked calculations, asset rights and limitations. Separate planned checks from passed checks. Record final PR/deployment evidence when available; do not mark publication verified until a production readback succeeds.

There must be one new essay at most per Korean publication date, and every essay after the original 30 must have a recorded date. If another run has already published or reserved that date, resume or close the duplicate instead of merging a second essay. Incorporate any changed base, then rerun the relevant checks on the actual merge candidate. Verify the exact commit tested, inspect the diff and wait for required checks. Merge within the user's authorization only after checks pass. Never force push over unrelated work or disable protection.
- Wait for the production deployment matching the merged commit. Fetch the actual canonical URL, home, RSS, sitemap and OG image; compare the content hash/date and incremented article count. A merge, build or HTTP 200 alone is not proof the new article is live.
- Report the live URL, useful content added, verification outcome and current essay count. If source quality, access, checks or deployment cannot be resolved, keep the reviewable draft and report the precise blocker. Do not publish unchecked material to meet a quota or claim a failed publication succeeded.

Daily publishing does not itself submit an AdSense re-review.
